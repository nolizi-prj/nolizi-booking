## OBJECT — I8 on the router

**I8** (and **I10**, of which I8 is an instance) requires the public `POST /signup` **response** to be identical for a newly created account and for `already_registered`. The spec says this has to be enforced **in the router**, because that is what production runs.

On a taken address the router returns a bare 200 and `loginPage(true)`:

```501:507:service/src/worker.ts
        if (isPublic) {
          if (claim.reason === 'ceiling') {
            return htmlResponse(400, signupPage('',
              'This service has reached its account limit and is not taking more.',
              { sso: ssoEnabled, publicSignup: config.publicSignup }));
          }
          return htmlResponse(200, loginPage(true));
```

On success it always forwards with `orgCookie: true`, including the public path:

```518:529:service/src/worker.ts
      return forward(claim.tag, {
        orgCookie: true,
        trusted: {
          'x-trusted-signup-email': email,
          'x-trusted-name': (form['display_name'] ?? '').trim(),
          'x-trusted-tz': (form['timezone'] ?? '').trim(),
          'x-trusted-new-org': claim.newOrg ? '1' : '0',
          ...(isPublic ? { 'x-trusted-verify-email': '1' } : {}),
        },
      });
```

`forward` then appends `Set-Cookie: pumasi_org=<tag>` (not HttpOnly). The HTML bodies match; the HTTP responses do not. Anyone can POST an address and tell new from existing by the presence of that cookie, and a new signup also leaks the org tag. That is the account-existence oracle I8 exists to forbid.

The unsharded `app.ts` path does not set this cookie, and `frontdoor.test.ts` I8 only compares status and body on `handle()`. There is no worker test. This is exactly the class of miss the spec warned about when it put the gate in the router.

Fix: `orgCookie: !isPublic` (the sign-in token is already tagged, so `/auth/<tag>.<token>` does not need the cookie). Then assert that success and `already_registered` match on status, body, **and** `Set-Cookie`, through the worker.
