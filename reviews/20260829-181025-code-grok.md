## OBJECT — D3: account deletion drops answers after the question is removed

Custom questions are specified to keep answers when the owner removes the question (label snapshot; the row is the record of what was asked). `booking_answers` has no foreign key to `event_questions` or `bookings`. Booker delete correctly goes by `booking_id`. Owner delete does not:

```1066:1069:service/src/app.ts
        await tx.query(
          `DELETE FROM booking_answers WHERE question_id IN
             (SELECT question_id FROM event_questions WHERE owner_id = $1)`, [owner.owner_id]);
        await tx.query(`DELETE FROM event_questions WHERE owner_id = $1`, [owner.owner_id]);
```

`DELETE FROM bookings` runs first and does not cascade. After a question has been removed, `event_questions` no longer contains that `question_id`, so the answers subquery matches nothing. The booker’s free text stays in `booking_answers` after the account is gone.

**D3** requires that an owner can delete their account and everything belonging to it, and that deletion removes the data. **D2** names those answers as booker personal data, the category “where deletion has to actually work.” The handler comment on remove says the answers “are deleted with the booking they belong to.” That is false on the account-deletion path the moment the question is gone.

The tests cannot catch this. `questions.test.ts` covers “remove question, answers remain” and “delete account while the question still exists” as separate cases and never composes them. `legal.test.ts` asserts the notice *says* deletion reaches answers; it does not run this sequence.

Fix: delete answers by the bookings that own them, before the booking rows go, e.g. `DELETE FROM booking_answers WHERE booking_id IN (SELECT booking_id FROM bookings WHERE owner_id = $1)`, and do not join through `event_questions`.

The same D3 hole exists on the booker’s link for series/collective bookings. Answers are written onto every occupied row, but the management token sits on the first row only and `/b/.../delete` clears that `booking_id` alone. Sibling rows keep the answers (and, pre-existing, the name and email).
